# 12 — i18n (`Support\Lang`)

Key-based translations backed by per-locale PHP array files — scales to a real, fully bilingual bot without one class per string (see [09 — Localized Text](09-texts.md) for the older `BotText` alternative).

---

## Setup

Point `lang_path` at a directory of locale files when calling `Bot::init()` (already wired up by `vendor/bin/devflow new`):

```php
Bot::init(env('BOT_TOKEN'), [
    'database'       => true,
    'lang_path'      => __DIR__ . '/../lang',
    'default_locale' => 'en',
]);
```

Each locale is a plain PHP file returning an array, `lang/en.php`:

```php
<?php

return [
    'welcome' => 'Hello, {name}! Welcome to the bot.',
    'menu'    => [
        'account' => '📋 My Account',
        'help'    => '❓ Help',
    ],
];
```

Nested arrays are addressed with dot notation: `menu.account`. `lang/fa.php` mirrors the same key structure with Persian values.

---

## Using it in a handler

```php
Bot::onCommand('start', function (Context $ctx) {
    $ctx->reply($ctx->t('welcome', ['name' => $ctx->from()?->firstName ?? 'there']));
});
```

`$ctx->t($key, $vars = [], $locale = null)` resolves the locale as:

1. The explicit `$locale` argument, if passed.
2. The user's **stored preference** (`telegram_users.language` — set via `$ctx->setLocale('fa')`).
3. Telegram's client-reported `language_code`.
4. The configured `default_locale` (falls back to `'en'` if unset).

If a key is missing from the resolved locale, it falls back to `default_locale`, then to the raw key itself (so a typo'd key is visibly obvious in the chat rather than silently blank) — unless `lang_auto_fallback` is on, see below.

### Falling back across every shipped language

By default, a key missing from both the resolved locale and `default_locale` renders as the raw key (`menu.account`), which is an obvious signal to you but a confusing one for the user reading it. Set `lang_auto_fallback` to search every other lang file you ship before giving up — a string in the wrong language is still more useful to someone than a raw key:

```php
Bot::init(env('BOT_TOKEN'), [
    'lang_path'          => __DIR__ . '/../lang',
    'lang_auto_fallback' => filter_var(env('LANG_AUTO_FALLBACK', false), FILTER_VALIDATE_BOOLEAN),
]);
```

Every time this actually fires, it logs a `WARNING` to `logs/YYYY-MM-DD.log` (never a live alert, never a crash) naming the key and which lang file it pulled from — so a missing translation shows up as a log line to fix, not a silent gap. Leave it `false` (the default) if you'd rather see the raw key than a wrong-language string.

### IETF/BCP-47 tag normalization

Telegram's `language_code` is a raw IETF tag, not necessarily one of your lang file names — a client can report `fa-IR` or `zh-Hans-CN` while your project only ships `lang/fa.php` / `lang/zh.php`. `Support\Lang` normalizes these automatically: it tries the full tag first, then drops one subtag at a time until it finds a lang file that actually exists — `fa-IR` → `fa`, `zh-Hans-CN` → `zh-hans` → `zh`. `Context::locale()` applies this on every call, so `fa-IR` correctly resolves to `lang/fa.php` instead of silently falling back to `default_locale`.

```php
use Devflow\TelegramBot\Support\Lang;

Lang::normalize('fa-IR');       // 'fa' (assuming lang/fa.php exists, lang/fa-ir.php doesn't)
Lang::normalize('pt-BR');       // 'pt-br' if lang/pt-br.php exists, else 'pt' if lang/pt.php exists, else 'pt' (bare primary subtag, even with no matching file)
```

`Lang::normalize(string $locale): string` returns the most specific tag that actually resolves to a lang file, falling back to the bare primary subtag (`pt-BR` → `pt`) if none of the tag's variants match a lang file at all. Use it wherever you want to persist a clean locale value — e.g. seeding `language` from `language_code` in `user_defaults` — instead of storing whatever Telegram sent verbatim:

```php
Bot::init(env('BOT_TOKEN'), [
    'database'      => true,
    'lang_path'     => __DIR__ . '/../lang',
    'user_defaults' => fn(\Devflow\TelegramBot\Types\Update $update): array => [
        'language' => Lang::normalize($update->message?->from?->languageCode ?? 'en'),
    ],
]);
```

## Locking every user to one language

Not every bot needs multi-language support. Set the `language_code` config key (or `LANGUAGE_CODE`
in a scaffolded `.env`, default `'auto'`) to a fixed code to ignore what each user's Telegram client
reports and force that language for everyone instead:

```php
Bot::init(env('BOT_TOKEN'), [
    'database'      => true,
    'lang_path'     => __DIR__ . '/../lang',
    'language_code' => env('LANGUAGE_CODE', 'auto'), // e.g. 'fa' to force Persian for every user
]);
```

This overwrites both the `language_code` and `language` columns on every update, so it also wins
over anything a user set previously via `$ctx->setLocale()`. Leave it at `'auto'` (the default) for
normal per-user locale resolution.

## Letting a user choose their language

```php
Bot::onCallbackQuery('lang_fa', function (Context $ctx) {
    $ctx->setLocale('fa');
    $ctx->reply($ctx->t('welcome', ['name' => $ctx->from()?->firstName]));
});
```

`setLocale()` persists to the `language` column, which takes priority over Telegram's `language_code` on every future `$ctx->t()`/`$ctx->locale()` call — unlike the legacy `BotText::forContext()`, which always preferred the Telegram client language.

## Translating reply-keyboard buttons

Reply-keyboard buttons send back their visible label as plain text, so you need to match the incoming text against *every* locale to know which button was pressed. `Lang::findKey()` does this reverse lookup:

```php
use Devflow\TelegramBot\Support\Lang;

Bot::onText(function (Context $ctx) {
    $key = Lang::findKey($ctx->text(), ['en', 'fa']);

    if ($key === 'menu.account') {
        // ... show account, regardless of which locale rendered the button
    }
});
```

## Outside of a `Context` (e.g. a broadcast or CLI script)

```php
use Devflow\TelegramBot\Support\Lang;

Lang::get('fa', 'welcome', ['name' => 'Ali']);
```
